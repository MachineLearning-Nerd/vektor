## Approach

> **Ordering matters.** The tag must point at the FINAL release commit (one that contains all README/roadmap/Phase-2/release-notes updates). Creating the tag earlier and then adding more commits afterward either makes the tag point at a pre-metadata commit, or causes the later `git tag` call to fail with "tag already exists." Steps 1-6 below land everything and wait for CI; step 7 tags; step 9 publishes.

1. **Pre-flight checks** — verify everything EXCEPT task 1.7 itself is done. Task 1.7's own row in the Phase 1 README is still ⬜ at this point (the release isn't tagged yet), so the check must explicitly exclude it:
   ```bash
   # Verify CI green on main. SCOPE TO THE CI WORKFLOW EXPLICITLY — without
   # --workflow=ci.yml, the most recent run could be Audit or another workflow,
   # so a green Audit could mask a failing CI workflow. Step 6 below uses the
   # same scope; keep them consistent.
   gh run list --branch main --workflow=ci.yml --limit 1 --json conclusion -q '.[0].conclusion'   # expect: success

   # Verify all Phase 0/1 tasks 0.1-1.6 are ✅ (excluding 1.7 itself).
   # Match emoji on the task ID rows specifically; ignore the 1.7 row.
   open_tasks=$(
     grep -E "^\| (0\.[1-4]|1\.[1-6]) " docs/plans/initial/phase-{0,1}*/README.md \
     | grep -v "✅" || true
   )
   if [ -n "$open_tasks" ]; then
     echo "FAIL: tasks 0.1–1.6 not all ✅:"
     echo "$open_tasks"
     exit 1
   fi
   echo "OK: tasks 0.1–1.6 all ✅"

   # Verify version in Cargo.toml
   grep '^version = ' Cargo.toml | head -1   # expect: version = "0.1.0"

   # Verify no Co-Author lines in commits since v0 baseline
   git log --format="%H%n%B" fc6a25b..HEAD | grep -i "co-author" && echo "WARN: Co-author present" || echo "OK"

   # Verify all tests pass under release profile
   cargo test --workspace --release
   ```

     ## Prerequisites

5. **Update tracker docs** — all in the working tree so they land in the single release commit:
   - `docs/plans/initial/phase-1-skeleton/README.md`: mark every Phase 1 task ✅ Done with its commit hash. For task 1.7's own row, write **`(release commit)`** as the permanent marker. **Do NOT try to backfill the real hash via `git commit --amend`** — amending changes the commit hash, which would invalidate whatever we wrote, in an infinite loop. A commit cannot reliably contain its own final hash; the `git log` is authoritative for "which commit was the release commit" via the `release: 1.7 —` prefix.

6. **Final commit + push, then WAIT for CI** — the tag must point at a CI-validated commit. The pre-flight CI check from step 1 validated `HEAD-before-this-commit`; it cannot validate the release commit itself because the release commit doesn't exist yet. So we push first, wait for CI, then tag.

   **Stage only the expected release files — DO NOT use `git add -A`.** `-A` stages everything untracked, which can pollute the release commit with stray binaries (a Mach-O `main` binary has appeared at the repo root twice during prior task work, and similar artifacts can creep in). Use an explicit pathspec:

   ```bash
   # Safety check: aside from the expected release files, the tree must be clean.
   # Anything unexpected gets caught here, not added to the release commit.
   UNEXPECTED=$(
     git status --porcelain | grep -vE "^.M? (README\.md|VEKTOR_ROADMAP\.md|release-notes-v0\.1\.0\.md|docs/plans/initial/(README|DEPENDENCIES)\.md|docs/plans/initial/phase-1-skeleton/README\.md|docs/plans/initial/phase-2-discovery-chunking/)" || true
   )
   if [ -n "$UNEXPECTED" ]; then
     echo "ABORT: unexpected files in working tree:"
     echo "$UNEXPECTED"
     echo "Investigate, clean, or extend the pathspec below before continuing."
     exit 1
   fi

   # Stage only what the release commit is supposed to touch.
   git add \
     README.md \
     VEKTOR_ROADMAP.md \
     release-notes-v0.1.0.md \
     docs/plans/initial/README.md \
     docs/plans/initial/DEPENDENCIES.md \
     docs/plans/initial/phase-1-skeleton/README.md \
     docs/plans/initial/phase-2-discovery-chunking/

   git status   # eyeball — confirm only the staged set above appears
   git commit -m "release: 1.7 — v0.1.0 release + Phase 2 task-file expansion

   ... (full message per AGENTS.md format)"

   # Push the release commit (NOT the tag yet)
   git push origin main

   # Wait for CI on the just-pushed commit
   RELEASE_SHA=$(git rev-parse HEAD)
   echo "Waiting for CI on $RELEASE_SHA..."
   sleep 20   # GitHub takes ~10-20s to register the triggered run
   RUN_ID=$(
     gh run list --commit=$RELEASE_SHA --workflow=ci.yml --limit 1 \
       --json databaseId -q '.[0].databaseId'
   )
   [ -n "$RUN_ID" ] || { echo "FAIL: no CI run found for release commit"; exit 1; }
   gh run watch "$RUN_ID" --exit-status --interval 60
   # gh run watch exits 0 only on success — if CI fails, fix and re-push BEFORE tagging
   ```

7. **Tag the (now CI-validated) release commit**. Tag only after step 6's `gh run watch --exit-status` returned 0:
   ```bash
   git tag -a v0.1.0 -m "v0.1.0 — Skeleton release

   First runnable Vektor binary. CLI parses, MCP server starts over
   stdio and registers 3 no-op tool handlers. No real indexing,
   embedding, search, or context assembly yet — those land in
   subsequent phases.

   See VEKTOR_ROADMAP.md Stage 2 and docs/plans/initial/ for the
   staged plan."

   git push origin v0.1.0
   ```

8. **Release-build step is SKIPPED at v0.1.0.** No binaries shipped from this phase (per Outputs section). Compilation is already proven by the CI run we waited for in step 6. The cross-platform binary pipeline (signed, checksummed, multi-arch) lands at v0.4.0 in task 6.2. At v0.1.0 the cargo source distribution + tag is the deliverable.

9. **Create the GitHub Release** — release notes only at v0.1.0; no binary attachments (per Outputs section above; binaries land at v0.4.0 / task 6.2):
   ```bash
   gh release create v0.1.0 \
     --title "v0.1.0 — Skeleton" \
     --notes-file release-notes-v0.1.0.md
   ```

## Notes / open questions

- **v0.1.0 is tag + release-notes only; v0.4.0 ships the binary pipeline**: this task does NOT build or attach binaries — that's task 6.2 / v0.4.0 scope per the roadmap. The "manual cross-platform build" language that lived here in an earlier draft was removed in round 2 (Phase 1 review) and round 5 cleanup. If you find yourself reaching for `cargo build --release` + `gh release upload` while executing this task, stop — that's scope creep into 6.2.
- **`gh release` requires gh CLI auth**: run `gh auth status` first; re-auth if needed.
- **Don't squash-merge releases**: tags should point at a specific commit. Squash-merging on GitHub can move the commit out from under the tag.
- **Phase 2 expansion is part of THIS task**: AGENTS.md says don't start Phase N without its per-task files. The release task is the natural place to do that expansion — fresh from shipping v0.1, the work for v0.2 is most clearly understood.
- **README badge accuracy**: a "pre-alpha" badge claiming there's no code is wrong after v0.1.0 ships. The shame is worse than the work — update it.
