# Task 0.1 — cargo init + Cargo.toml

**Phase**: 0 — Scaffolding
**Task ID**: 0.1
**PRD reference**: Section 11 (Technology Stack — Cargo.toml skeleton)
**Roadmap stage**: Stage 2 prerequisite (pre-`v0.1.0`)
**Effort estimate**: S (≤1h)
**Depends on**: none
**Blocks**: 0.2, 0.3, 0.4, 1.1

## Objective

Bootstrap the Vektor Rust project in the repo root. Create `Cargo.toml` with the exact resolved dependency set from PRD Section 11, create `src/main.rs` with the standard `fn main()` stub, verify `cargo check` succeeds, and ensure the binary builds against `edition = "2024"` and `rust-version = "1.91"`.

This task gives the repository its **build identity**. Every later task assumes `cargo check` works.

## Inputs (must exist before starting)

- `VEKTOR_PRD.md` Section 11 with resolved Cargo.toml (already committed)
- `.gitignore` already covers `target/` and `*.rs.bk` (committed in `025e522`)
- A working Rust toolchain ≥1.91 (`rustup toolchain install 1.91` if needed). The 1.91 floor comes from `lancedb 0.29`'s transitive `lance` crates, not from `ort` (whose MSRV is the lower 1.88).

## Outputs (must exist after completion)

- `/Cargo.toml` — the dependency manifest, copied verbatim from PRD Section 11 Cargo.toml block
- `/src/main.rs` — `fn main() { println!("vektor"); }` stub
- `/Cargo.lock` — generated by `cargo check`; **committed** because Vektor ships as a binary, not a library
- `/rust-toolchain.toml` — pin the toolchain version so contributors land on 1.91+

## Approach

1. Verify Rust toolchain: `rustup show active-toolchain`. If below 1.91, run `rustup install 1.91 && rustup default 1.91`.
2. Create `/Cargo.toml` from PRD Section 11. Copy the block exactly. Do not add or remove anything.
3. Create `/src/main.rs` with the simplest possible stub:
   ```rust
   fn main() {
       println!("vektor");
   }
   ```
4. Create `/rust-toolchain.toml`:
   ```toml
   [toolchain]
   channel = "1.91.0"
   components = ["rustfmt", "clippy"]
   profile = "minimal"
   ```
5. Run `cargo check`. This downloads + resolves dependencies. Will take 5–15 minutes on first run.
6. If `cargo check` fails on a specific crate, **do not relax versions**. The PRD Section 11 versions were resolved against current crates.io; failures here mean an environmental issue (toolchain too old, network problem, etc.). Fix the environment, not the manifest.
7. Verify `Cargo.lock` was generated. Stage and commit it.

## Acceptance criteria

- [ ] `cargo check --workspace` exits 0
- [ ] `cargo build --release` exits 0 (builds the binary)
- [ ] `target/release/vektor --help` exits 0 (even if help is trivial)
- [ ] `Cargo.lock` is committed to git
- [ ] `rust-toolchain.toml` pins to 1.91
- [ ] No version in `Cargo.toml` differs from PRD Section 11 (use `diff` to confirm)
- [ ] `cargo tree -d | grep -E '^(arrow|lance)'` is empty (the v2.3 PRD's specific concern about Arrow/Lance version coupling). General duplicate transitive deps elsewhere in the graph are allowed — the Rust ecosystem produces ~40 of them from a stack this size (base64, bitflags, hashbrown, getrandom, reqwest, sha2, syn v1/v2, etc.). Strict zero-duplicates is unachievable without forking deps. Tightening this gate is a Phase 6 supply-chain task (C8.6 SBOM-time analysis).

## Verification

```bash
# Toolchain
rustup show active-toolchain | grep -E "1\.(8[89]|9[0-9])"

# Build
cargo check --workspace 2>&1 | tee /tmp/vektor-check.log
[ $? -eq 0 ] || { echo "FAIL: cargo check"; exit 1; }

cargo build --release
[ -f target/release/vektor ] || { echo "FAIL: no binary"; exit 1; }

# No duplicate transitive deps (especially arrow*)
DUPS=$(cargo tree -d 2>/dev/null)
if [ -n "$DUPS" ]; then
    echo "FAIL: duplicate deps detected:"
    echo "$DUPS"
    exit 1
fi
echo "OK: no duplicate deps"

# Print the [dependencies] section for visual cross-check against PRD Section 11.
# Uses a state-machine awk that handles the case of [dependencies] being adjacent to
# the next [section] heading. (The earlier `awk '/^\[dependencies\]/,/^\[/'` pattern
# was broken: when the range start AND end pattern match on the same line, awk's
# range terminates immediately, emitting only the [dependencies] header — and then
# sed '$d' deletes that one line, producing empty output.)
echo "--- Cargo.toml [dependencies] section: ---"
awk '/^\[dependencies\]/{flag=1; next} /^\[/{flag=0} flag' Cargo.toml
echo "------"
echo "Visual cross-check: confirm versions match VEKTOR_PRD.md Section 11."
echo "A byte-level diff against the PRD is not run automatically because the PRD's"
echo "TOML block has comments that don't round-trip through cargo's manifest parser."
```

## Notes / open questions

- **ort 2.0.0-rc.12 download**: First `cargo check` may take 10+ minutes because `ort` downloads ONNX Runtime binaries (~200MB). Be patient. If the download hangs, set `ORT_DOWNLOAD_TIMEOUT=600` env var.
- **`bundled` feature on rusqlite**: this compiles SQLite from source. Adds ~1 minute to first build but means we don't depend on system SQLite version.
- **Crate name**: PRD/roadmap acknowledges `vektor` is taken on crates.io. For local builds this doesn't matter; we only need to rename at `cargo publish` time. Use `vektor` in `Cargo.toml` for now and flag this as a known issue (already in `VEKTOR_ROADMAP.md`).
- **`cargo new` vs manual setup**: don't run `cargo new` — that creates a new directory. We're initializing in the existing repo root. Manually create the files.
- If `cargo check` succeeds but the dependency tree pulls in surprising crates (e.g., a windows-only crate transitively), check `cargo tree -i <crate>` to understand the chain and document anything weird in this Notes section.
- **MSRV gotcha (2026-05-28 incident #1)**: When PRD Section 11's Cargo.toml was first resolved via `cargo new && cargo add` on 2026-05-27, the throwaway project had no `rust-version` declared, so the resolver did NOT enforce per-dep MSRV. The result: `lancedb = "0.29"` was accepted even though its transitive `lance` crates require rustc 1.91. The PRD was then annotated with `rust-version = "1.88"` based on `ort`'s MSRV alone. Task 0.1's first execution surfaced this conflict (lance@6.0.0 + lance-core@6.0.0 + 11 sibling lance crates all require 1.91). Fix: bumped pin to 1.91. **Lesson for future Section 11 refreshes**: after running `cargo add ...`, ALSO write the intended `rust-version` into the throwaway project's Cargo.toml and re-run `cargo check` — that forces MSRV enforcement and surfaces conflicts before they hit task execution. Don't trust `cargo info ort | grep rust-version` alone; check every dep's MSRV explicitly via `cargo deny check` or by parsing `cargo metadata --format-version 1 | jq '.packages[] | {name, rust_version}'`.
- **libsqlite3-sys cfg_select gotcha (2026-05-28 incident #2)**: After fixing the MSRV gap, task 0.1's second execution failed at the *compilation* phase. `rusqlite = "0.40"` pulls `libsqlite3-sys = "0.38.0"`, whose `build.rs` uses the `cfg_select!` macro — a feature still unstable in rustc 1.91, 1.92, and 1.93.1 (tracking issue rust-lang/rust#115585). Cargo's MSRV check doesn't catch this because `libsqlite3-sys` declares `rust-version = unknown`; the error only fires during compilation. Fix: downgraded to `rusqlite = "0.39"` which pulls the working `libsqlite3-sys = "0.37.0"`. **Lesson for future Section 11 refreshes**: `cargo new && cargo add && cargo check` (not just `cargo add`) is the only complete validation. Even MSRV-correct dep graphs can ship unstable-feature usage on stable Rust. Validate compilation, not just resolution. The PRD's `rusqlite` pin must be revisited periodically until `libsqlite3-sys 0.38.x+` drops cfg_select usage or 1.94+ stabilizes the feature.
